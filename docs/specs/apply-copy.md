# Apply and Copy

> **Status:** implemented on Windows (Phase 0). In Word, Apply edits the document in place and keeps the formatting (Phase 2, APL-40 to APL-45).
> **Source:** `src-tauri/src/commands.rs` (`apply_text`, `copy_text`), `platform/mod.rs` (`apply`, `paste_into`, `copy_text`: the same flow on every platform), `edits.rs` (the word-level diff), Windows: `platform/win/mod.rs` (`is_in_front`, `bring_forward`, `send_paste`), `word/`, `clipboard.rs`, `input.rs`, `window.rs` (`focus`); `src/popup/Popup.tsx`.

Apply puts the chosen version back in place of the selection; Copy leaves it on the clipboard for the user to paste wherever they like. Both use the restored text (placeholders swapped back, [privacy.md](privacy.md) PRV-14) and only a ready variant ([popup.md](popup.md) POP-32). A variant that lost a masked value is offered for Copy only ([popup.md](popup.md) POP-34).

## Apply

- **APL-01** Apply closes the popup and cancels the running request, then works on its own thread so the UI never waits.
- **APL-02** It brings back the window that was in front when the selection was captured: it restores the window if minimized and asks Windows to focus it. Windows only lets the process that received the last input change the foreground, so ToneSnap falls back to attaching to the current foreground thread's input queue. It retries every 40 ms for up to 800 ms.
- **APL-03** Once the window is in front, ToneSnap waits 80 ms (the app restores its caret and selection), snapshots the clipboard, puts the text on it as a transient entry ([privacy.md](privacy.md) PRV-31), waits up to 400 ms for modifier keys to be released, and sends Ctrl+V.
- **APL-04** It waits 500 ms before restoring the user's clipboard, because Electron apps (Slack, Teams…) read the clipboard asynchronously and would otherwise paste the old content.
- **APL-05** If the window could not be focused or the clipboard could not be written, the text is copied to the clipboard as a normal entry and the `apply_failed` notice tells the user to press Ctrl+V. In that case the clipboard is intentionally **not** restored.
- **APL-06** Apply relies on the app's own paste: the text replaces the selection only if the app still has it selected when it gets focus back. How each app behaves is recorded in the compatibility table of `docs/PLAN.md`.
- **APL-07** Apply needs a session; without one the command fails with "no session" and nothing happens.

## Word

When the capture read the selection from Word itself ([capture.md](capture.md) CAP-24), the session keeps an anchor (the document pane, the selection's offsets and its text) and Apply edits the document instead of pasting.

- **APL-40** A word-level diff of the captured text against the chosen version gives the spans to replace (`edits.rs`: words, runs of spaces and every other character are tokens; a line break is a token of its own, so a change of indentation never replaces a paragraph mark). Words that did not change are not touched and keep their formatting (bold, italics, links, styles); a replaced span takes the formatting of its first character, inserted text the formatting before it. Over 100 spans, or over a million token pairs to compare, the part that differs is replaced in one piece. Links and other fields (CAP-25): a span inside a link's visible text is edited in place, so the link keeps its address; text inserted next to a link goes outside it, and between two of its characters inside it; a span that reaches across a link's edge grows to the link's whole text and replaces the link, its unchanged words kept as plain text.
- **APL-41** Before any edit, ToneSnap reaches the document again from the same pane and checks that the text at the captured offsets is still the captured text. If the user edited it meanwhile, the range now holds tracked changes, or Word cannot be reached, nothing is changed and Apply pastes as in APL-02 to APL-06. Word's selection still holds the paragraph marks the capture left out (CAP-25), so the pasted text gets them back and paragraphs are not merged.
- **APL-42** The spans are replaced from the last to the first, so the offsets of the others stay valid, inside one Word undo record named "ToneSnap": one Ctrl+Z in Word undoes the whole Apply. Line breaks in the answer, `\n`, `\r\n` or `\r`, are each written as one paragraph mark. With Track Changes on, the edits are recorded as revisions like any other; the deleted words stay in the document, so a second Apply over the same text pastes (APL-41). The caret ends after the new text, as after a paste, with or without Track Changes, and Word is brought back to the front.
- **APL-43** If an edit fails after others were made, the undo record is closed and undone, the text goes on the clipboard and the `apply_failed` notice shows (APL-05). If the first edit fails, nothing changed and Apply pastes instead.
- **APL-44** Word busy (a dialog open, a long operation) turns calls away; each call is tried again up to 3 times, 50 ms apart, the undo record's start included. Apply waits at most 3 s for Word to start editing. If it has not started by then, Apply reports `apply_failed` with the text on the clipboard, and a late answer from Word changes nothing: the thread talking to Word must claim the edit before its first change, and cannot once Apply has given up. If Word has started editing, Apply waits for it to finish, however long that takes, so the user is never told to paste text Word is still writing.
- **APL-45** The COM calls run on a dedicated MTA thread; no COM object is kept between the capture and Apply, only the pane's window handle, the offsets and the text. While an earlier call to Word is still waiting (CAP-26), Apply pastes instead.

## Copy

- **APL-10** Copy closes the popup and cancels the running request ([ai-request.md](ai-request.md) AI-54), then puts the text on the clipboard as a normal entry, so it appears in clipboard history like any copy the user makes.
- **APL-11** The clipboard write runs on its own thread and retries for about 300 ms (20 tries, 15 ms apart), because another app can hold the clipboard open for a moment.

## macOS

- **APL-30** Same flow with Cmd instead of Ctrl (`platform/mac/mod.rs`, `input.rs`, `clipboard.rs`): the app is found by the process id kept in the session's `target`, brought forward if needed (800 ms), the text is placed as a transient entry (`org.nspasteboard.TransientType` and `ConcealedType`, which clipboard managers skip), and Cmd+V is posted after the modifiers were released. The snapshot keeps every item and every type on the clipboard. Posting keys needs the Accessibility permission. The C and V keys are looked up on the current Latin layout (`UCKeyTranslate` over the key codes, refreshed on the main thread at startup and before every capture), since macOS reads a Cmd shortcut's letter from there; Dvorak and AZERTY work, and the US key codes are the fallback.

## Read-only fields

- **APL-20** When the capture reported the field as not editable, Apply is not offered and the number keys copy instead ([popup.md](popup.md) POP-35). When editability is unknown, Apply is offered. How editability is found, including the selected text's read-only attribute that tells editable web fields from page text: [capture.md](capture.md) CAP-07.
